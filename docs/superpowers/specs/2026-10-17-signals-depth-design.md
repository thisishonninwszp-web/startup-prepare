## 一、去掉空话

### 规则(纯函数,不多调 AI)

`dropEmptyConclusions(text) → { text, dropped }`,放在 `lib/ai/signals.ts`,和 `dropFillerSentences` 放一起:

| 情况 | 处理 | 例子 |
|---|---|---|
| 整句只是在评论上一句:以「这/此/此举/这些/这也/这种/这一(变化、举措……)」开头,紧接着「表明/意味着/反映/体现/凸显/标志着/预示/说明」 | 整句删掉 | 「这表明日本政府高度重视个人信息保护问题,并敦促各企业加强防范。」→ 删 |
| 前半句是事实,后半句以「,(这/此举)(也)表明/意味着/反映出/反映了/体现了/凸显了/标志着/预示着」接上 | 删掉逗号后面那半句,句号补回 | 「调查还显示,不到两成的令牌支出能证明与量化财务成果相关联,这意味着许多AI投资未能带来明确的业务效益。」→ 留「……相关联。」 |
| 句子里有具体的人和事,只是用了「趋势」「日益」 | 不动(宁可漏删,不删事实) | 「这种国际趋势可能会影响日本央行……例如瑞穗银行已开始上调其储蓄存款利率。」→ 留 |

- 全删光就原样返回(和 `dropFillerSentences` 一样,交给上游)。
- 实现时拿上面这几句真实的句子当测试样本,再从库里最近两周的条目干跑一遍,看删掉的句子里有没有事实。

### 用在哪

- **生成时**:五节条目的 background、for_you、precedent,草稿(`parseBrief` 那一步)和读完正文重写(`parseGroundedBrief`)都过一遍。
  删掉的句子存在条目上(`BriefItem.dropped?: string[]`)。
- **显示时**:旧报告没过这一遍。读报告(`lib/domains/signals/brief.ts` 读 signal_briefs 的两处)和读差距清单(`lib/domains/signals/gaps.ts`)时再过一遍,
  所以过去两周的报告、差距清单的背景、周刊取的料也是干净的。规则对已经删过的文字不会再删(幂等)。
  其他把旧报告当材料喂给 AI 的地方(周报、历史题、问题页)不改 —— 新报告生成时已经删过。
- **提示词**:`SIGNAL_SHARED_RULES` 加一条:背景的最后一句写事实(谁做了什么、数字、日期);
  不许用「这表明/这意味着/反映了/预示着/标志着/凸显了」给前面的事下结论;想说影响,写成具体谁会做什么。

### 防止删错

- 信息源体检页(/signals/sources)加一行:「最近 7 天删了 N 句」,点开看删了哪些(按天、按节)。只数次数。
- 删错了的样本就改规则,不加"恢复"按钮。

## 二、「一条讲透」页

### 入口和地址

- `/signals/gaps/deep?side=japan|us|china&id=<signal_id>`,不加导航。
- 入口:差距清单每条旁边「一条讲透」;周刊挑条时每条也有这个链接。
- 这条从差距清单里消失了(比如超过两周、被挪进"有了"),页面照样能打开:按 side + id 从存下的报告里找,找不到就说"这条找不到了"。

### 页面从上到下

| 节 | 内容 | 来源 | 没有时 |
|---|---|---|---|
| ① 那边是怎么回事 | 报告里的背景和原文依据(basis) + 「那边查一查」的事实 | 已有 + **新** | 按钮「那边查一查」 |
| ② 这边现在怎样 | 进清单时的核实(带出处)、每月重查的记录 | 已有 | —— |
| ③ 能不能搬过来 | 3–5 个条件成立/不成立/说不清 + 有没有人试过 | 已有(`signal_gap_transfers`) | 按钮,调现有的 `analyzeGapTransferAction` |
| ④ 这边有人在为这个头疼吗 | 那件麻烦、真人原话、三种各几句 | 已有(`signal_gap_voices`) | 按钮,调现有的 `analyzeGapVoicesAction` |
| ⑤ 同类东西以前来日本的结果 | 他点这条属于哪一类 → 同类先例(东西、隔了多久、结果)+ `baseSentence` | 时差图谱 | 先点类别 |
| ⑥ 官报里看得到的 | 对上的官报决算(用现有的 `NoticeLine`) | 官报 | 写明"没对上不代表没登" |
| ⑦ 有没有人掏钱 | 日本拉到投资的公司、假门看了几次留了几个邮箱、周刊读者回应(有痛/问价各几个) | 已有 | 各自写"还没有" |
| ⑧ 你的判断 | 周刊那三下(会/不会/说不清、最大的阻碍、谁最可能先做)+ 补一句 | 已有组件 | —— |

- 最上面一个按钮「把缺的都查一遍」:①③④里没查过的,一步一个请求按顺序跑(每步 60 秒内),跑完一步显示一步,失败的那步写原因、别的照跑。
- 页面最下面「用这一条写一期」:跳到周刊,只选这一条,判断带过去。
- ⑧ 点的判断在这页先存着(下一节的表里),到周刊页还在;真正押进判断账本照旧是第一次记"发了"的时候。

### ① 那边查一查(唯一新的 AI 步骤)

- 语言跟着"那边":side=japan 那边是中国 → 中文搜;side=us → 英文搜;side=china 那边是日本 → 日文搜。
- 两次 `webSearch`:「谁在做、做到多大」和「怎么收钱、哪一年开始」;AI 先写搜索词(不带"日本"),搜完看着资料摘事实。
- 最多 6 条事实,每条:一句中文 + 原文摘录 + 网址。代码核对:
  - 摘录逐字在那一页上(和现有的核对同一套);
  - 事实里的数字(阿拉伯数字和汉字数字都算)必须在那句摘录里;事实里点名的公司名必须在摘录里。
  - 对不上的丢掉;丢完一条不剩就写"没查到能对上原文的",不留 AI 的话。
- 不写"所以""说明"这类结论句(过一遍上面的去空话规则,再查 SIGNAL_BANNED)。
- 存进新表(见下),同一条可以"重查一遍",新的覆盖旧的。

### ⑥ 官报对哪几家

只做完全相同的公司名匹配(归一化后相同,现有的 `companyKey`),不让 AI 猜日本法人叫什么:

1. ⑦ 里日本拉到投资的那家公司(`gap.funded.company`)→ `latestNoticeFor`。
2. 他的「在日本的中国公司」名单里,中国那边的名字(`name_zh`)原样出现在这条的标题、背景或①的事实里的 → 显示名单上对上的决算。
3. ⑤ 里同类先例,有官报决算的(现有的 `caseNotices`)→ 在先例那一行旁边显示。

## 三、周刊怎么用这些料

- **不另做"深度模式"**。`IssuePick` 多带几样(都是可选,查过才有):
  `there`(①的事实)、`voices`(④的麻烦、三种各几句、最多 3 句原话)、`benchmark`(⑤的那句基准)、`kanpo`(⑥对上的决算,一行)。
  `buildPick` 从服务器按 id 取,不信浏览器。
- 提示词的结构改成:那边是什么(①)→ 这边现在怎样(②)→ 为什么还没有(③)→ 这边有人在头疼吗(④)→ 以前同类的结果(⑤)→ 官报(⑥,给了才写)→ 我的判断。
  给了才写,没给的不提。挑 1 条就是一篇讲透的,挑 3 条还是现在这样。
- 代码多核对一样:中文稿和日文稿里 AI 写的部分(去掉他的原话以后),每个数字都要在给它的料里出现过;对不上就作废重写(现有的重试机制)。
  年份、"2 年"这类来自料和判断的数字自然通过。
- 出处列表照旧由代码拼,加上①④的网址。

## 不做的

- 「那边查一查」不进每天的定时任务(两个 cron 都满了),只在他点的时候跑。

## 10-17/18 改「那边查一查」的搜法（试了四轮，按定的规矩换）

- 起因：真跑点淘那条，搜出来的多是「点淘能不能赚钱」的博客，留下 1 条，没有规模数字。
- 先试了哪些商业媒体代码读得到：中文 36氪、界面、钛媒体、21财经、澎湃、第一财经全文；英文 TechCrunch、Business Insider、GeekWire 全文但偏旧；日文日経、ITmedia、朝日只有七八十字摘要。晚点、虎嗅、亿邦、QuestMobile、财新没出来。
- 四轮对比（同样 3 条：点淘、Amazon 的 AI 设备、日本豆芽；看「做到多大」里真的规模数字）：
  1. 只用一个叫法、限商业媒体：点淘 0 条（搜到的讲淘宝直播，被当成别的东西跳过）——没过。
  2. 加搜母公司、允许摘母公司那块业务的数字：点淘 2 条（淘宝直播 GMV 超 4000 亿等），豆芽 1 条（AI 把叫法写成了一家公司），Amazon 0 条。
  3. 叫法只许写东西本身：豆芽好了，点淘的叫法变成「短剧直播电商」，摘到的是红果短剧、抖音的数字——变差。
  4. 产品名 + 这一类东西两个叫法一起搜：点淘 3 条、Amazon 0 条、豆芽 2 条，没有一条比第 2 轮差，换成这一版。
- 结论：只给一个叫法时 AI 每次写得不一样（产品、一类、公司），料跟着大起大落；两个叫法一起搜才稳。Amazon 那条（Bee）两版都没有规模数字，商业媒体上就没写。
- 样本只有 3 条，旧版两次跑结果也不一样，噪音不小；以后再改搜法照样先拿几条做新旧对比。
