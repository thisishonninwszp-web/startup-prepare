# 每日一门生意：产品与数据设计

日期：2026-10-28。状态：已根据用户认可的方向整理为设计，尚未开发、接入新来源或启用定时任务。

配套：[分期实施计划](../plans/2026-10-28-daily-business-teardown-plan.md)。

## 1. 产品目标

每天研究一家没拆过的店铺，以主打商品切入，用相近店铺作对照，理解顾客购买、商家成交、实际交付和生意成立的条件，最后留下能借鉴的方法、未解释的问题与一个最小验证动作。

它服务于“成为能经营的人”和下一次验证行动。不把热门商品直接推荐为用户应当做的项目，不给想法或店铺打综合分，也不把分析完成计为真实接触。

**选定的分析单位：一家店的整盘生意。** 一个主打商品负责让材料具体；对照店负责检验解释。单品包装、文案、价格只是其中的经营手段，不代替获客、交付与复购分析。

取舍：只拆爆款容易脱离履约和经营；一次写整个行业容易缺乏具体依据。第一版采用“店铺＋主商品＋对照店”，在可核对的材料范围内拆解，不声称掌握商家后台。

## 2. 用户每天看到什么

首页放“今日生意”入口，详情与历史位于 `/business-lab`，归入现有“成长”导航。未开启时不显示入口，原新闻阅读和30秒捕捉不变。

页面分三层：

1. **先读摘要**：这家店卖给谁、卖什么、最值得核对的成交解释、最大的未知；附商品/店铺原链接和材料日期。
2. **展开拆解**：沿下表阅读全文，来源原话和结构化字段可逐项展开。
3. **留下一点自己的东西**：确认一个可借鉴的方法、补充一个反例，或预览一个验证动作。均可不填，不把阅读变成考试。

| 模块 | 必须回答 | 材料不足时的表现 |
| --- | --- | --- |
| 店铺与商品 | 谁在经营、主商品、价格、规格、套餐、承诺、材料覆盖哪些商品 | 保留已知范围，不称已分析全店销售结构 |
| 购买触发 | 什么任务或生活事件使人此刻需要它 | 写待核对的情境假设，不能编造顾客原话 |
| 顾客与购买量 | 谁可能在什么场景买；自用/送礼；包装、下单件数、复购线索 | 未知单独保留，不外推整店顾客比例 |
| 热销依据 | 公开销售显示、排名、评价等到底说明了什么，属于哪个时段/榜单 | 只描述实际观察，不能把评价数变成销量 |
| 购买过程 | 从发现、搜索、比较、犹豫到下单、收到、使用的各环节 | 区分实际评价叙述和待验证的路径 |
| 顾客付钱买什么 | 商品之外是否买了省事、确定性、匹配建议、交付速度等 | 给出竞争解释及能区分它们的新材料 |
| 经营动作 | 选品、备货、内容、客服、发货、退换货各有什么负担 | 不假定几个人、一周几小时即可经营 |
| 收入与成本 | 售价、套餐、加购/复购线索、公开成本与履约条件 | 没有成本就不写真实利润或净利率 |
| 对照分析 | 相近店铺哪些条件相同、哪些不同，解释是否仍成立 | 不能仅凭评价少判为失败，也不强做不可比对照 |
| 失效条件 | 停补贴、流量变贵、涨运费、断货等会影响哪一环 | 写条件推演，不宣称这些事已经发生 |
| 借鉴与改进 | 哪些能迁移、依赖什么资源、哪些改动只是增加成本 | 每条建议含目标问题、依据、代价、反例和检验办法 |
| 最小验证 | 用户当前资源允许做什么，做完能知道什么 | 公开核对/原型测试仍不能替代痛点和付费验证 |

每篇结尾固定保留：**一个可借鉴的方法、一个仍没解释通的问题、一个最小验证动作。** 没有可借鉴项时可以明确记录条件不适用，不强行凑建议。

## 3. 数据怎样支撑这些问题

### 3.1 乐天第一条自动来源

现有 `lib/rakuten.ts` 已封装商品搜索。官方商品搜索当前为2026-07-01，排名接口为2022-06-01，均需applicationId和accessKey。执行时仍须做一次凭证/请求返回结构的实际核验，不能把文档可查等同于接口已接通。

可用入口包括店铺/商品代码、名称、简介、价格、包装说明、配送/积分条件、评价数量和榜单名次。榜单必须保存类目/人群筛选、更新时间、页码及实际覆盖；年龄/性别榜的出现只说明出现在该分组榜单，不说明全部顾客构成。官方排名接口的genre与age/sex筛选不能任意组合。

项目现有“按评价数排序”的搜索结果不能称为销量排行。新功能需要单独的排名适配与来源标识，不偷偷改旧搜索语义。

### 3.2 小红书第一版路径

支持用户提交店铺/商品/笔记链接，以及选择粘贴的公开摘录或截图转写文本，标明手动提供、捕获日期、出处及可见范围。只从实际提供内容提取店铺、商品与购买情境；链接打不开或材料不完整时明确缺失。

官方电商开放平台面向店铺授权场景，不预设可取得任意商家的订单、销量和买家资料。已有采集worker能否处理个别链接，不等于具备稳定、完整、获准的店铺数据接口。第一版不接用户cookie、不绕过登录/验证码、不自动采集私人顾客资料。

后续取得明确的商家授权或可用的数据供应接口时，以新来源适配接入，保留费用、覆盖、更新频率和授权范围；不得把第三方估计标成平台实测。

### 3.3 原话与数据的边界

- 来源逐字摘录原样保存和显示；清除买家昵称、头像、个人联系方式等非必要信息。评论中的个人自述不外推为全体买家。
- 摘录、商家自述、平台显示、用户补充和模型解释有各自出处，不做证据强弱等级。
- 商家称“累计售出”仍标商家声明；平台标“已售1万+”保留下界、单位和未说明的时段，不变成精确销量。
- 数据空缺用null及缺失原因；0只能来自明确零值。获取失败不是零销量、店铺停业或需求消失。
- 只保存适配器允许保留的字段和必要摘录；展示归属与原链接，实施时核对平台使用/缓存条件，不默认完整评论和图片可无限复制存储。

### 3.4 “买多少份”的五个不同量

| 量 | 能怎样记录 | 不能推出什么 |
| --- | --- | --- |
| 包装含量 | “每袋12枚”，单位为包内件数 | 12个买家或每单买12袋 |
| 单次下单件数 | 一条实际材料写“买了3盒”，注明只是该条叙述 | 全店平均每单3盒 |
| 公开销售显示 | 保存原值/下界、件/单等单位和累计/近期时段 | 评价数、独立买家数或当前月销量 |
| 复购线索 | 记录“再次购买”等来源叙述及样本范围 | 整体复购率和复购周期分布 |
| 客单价 | 有同一订单的实际件数/金额材料时记录；否则未知 | 用标价乘虚构件数推算真实客单价 |

评价样本描述不能生成总体年龄、性别、收入分布。平台分组榜、包装选择和具体评论可以提出人群假设，但必须保留反例与覆盖限制。

## 4. 每日不重复与选题

### 4.1 去重规则

1. 每个用户按东京自然日只有一个主案例槽位；多设备、重复刷新、worker重试都返回同一个槽位。
2. 以平台稳定店铺ID识别店铺，换商品仍算同一家店；商品ID用于材料去重，不用来绕过店铺去重。
3. 已分配、已读和已跳过的主案例都占用历史。失败重试继续处理同一槽位，不因为刷新不断换店。
4. 跨平台只有在经营主体对应关系被核对后才合并去重；名字相似不自动合并。身份无法确认时明确“不保证跨平台经营主体唯一”。
5. 后来确认两家其实同一经营主体，追加身份修正与历史重复提示；不删除旧日记录。未来选题按合并后的集合排除。
6. 对照店可以复用既有案例，标明已见案例并链接；每日新主案例仍不可复用。
7. 没有合格新候选或来源不可用时，显示今日未完成及原因；不拿旧案例充当新案例，不编造完整数据。

### 4.2 选题机制

先用二元准入检查：店铺身份可定位、至少一个商品有可核对材料、来源未被用户排除、未被主案例历史使用。再按预先保存的行业/价位/经营方式轮换规则选取，排序和tie-break固定可复现，不产出机会总分。

候选材料覆盖须说明：排名前N、用户提供的单个链接、指定关键词搜索页或店铺部分商品，不能叫全平台普查。既看热门候选，也给非头部但材料充分的经营案例留轮换入口，降低只学到幸存者的偏差。

第一版时间默认东京07:00为产品建议，可改。不开启自动运行时，用户当天首次打开后触发准备；开启后才按约定预生成。没有启动的timer不显示为后台已运行。

## 5. 对照与经营解释

比较双方至少记录商品用途、规格/数量、价格构成、配送地域与时效、促销/积分、时间窗口、榜单范围。不同币种/套装/样本不能直接下“更便宜、更畅销”的结论。

每个成交解释同时写：支持的材料、至少一种竞争解释、什么新观察能区分、在哪些条件下不成立。存在相关现象不等于知道因果；“销量表现不同”也不能证明其中一家的文案导致差异。

改进建议以实际购买疑问、负面体验、履约约束为入口。不能因为能加功能就建议加功能；同样允许建议减少规格、停止承诺、简化包装或暂不改动。

成本分为公开可核对值和用户明确设定的情景参数。后者只做“若这些假设成立”的计算，公式由代码计算，不填成商家的真实成本或利润。

## 6. AI的任务与授权

AI只基于冻结材料提出解释与反驳，输出带来源指针的结构化章节。提示目标是找出解释不成立、不可迁移和生意可能做不下去的条件；禁止“很有潜力”“照做能成功”等迎合结论。

对外发送前展示数据范围：店铺/商品公开字段、用户明确选择且去标识的摘录。历史笔记、私人反馈、原型事件、商家授权订单和买家身份默认不发送。既有新闻AI许可不自动覆盖本模块。

逐次生成需要明确确认；每日自动生成另有可撤销的范围授权，保存授权版本/允许来源/有效状态和预算。扩展到新平台或新数据种类须重新确认范围。授权关闭、过期或范围不符时只准备材料，不调用Gemini。

所有调用经过 `lib/ai.ts` 对应统一入口及现有gateway，模型读取AI_MODEL。来源内容为不可信输入，不能执行其中的指令。服务端验证sourceID、逐字引用、数值来源、输入清单哈希；不允许AI生成未提供的销量、顾客比例和真实利润。

材料变化后追加报告版本，保留当时材料与解释。模型输出校验失败、超预算、截断或接口失败时显示原因，保留可读材料，不假装已有完整分析。

## 7. 与现有功能怎样联动

| 现有能力 | 连接方式 | 边界 |
| --- | --- | --- |
| 材料/观察 | 用户选中一个经营方法或反例，预览后存为观察并附案例版本出处 | 不批量灌入未阅读AI文案 |
| 想法与信息缺口 | 用户选择本人想法，填写适用范围和未知，再确认引用 | 不是需求成立，不改状态/计时 |
| P1A/P2实验与搜索观察 | 将“可区分两种解释的问题”预填为实验草稿或观察问题 | 用户核对后走既有保存入口，不自动生成真实验证 |
| P3企业身份 | 可用已确认的主体关系协助店铺去重，保留身份依据 | 同名不自动认定同一经营者 |
| P5解释与来源纠错 | 复用纯比较/引用核验思路，案例内追加纠错影响 | 不能直接把不兼容snapshot ID写进旧事件表 |
| P6调度 | 复用租约、请求预算、失联重试的机制 | 现有118绑定e-Stat，不能直接塞入乐天店铺配置 |
| 学到了/周复盘 | 只沉淀用户确认的方法与失效条件，附当时引用 | 自动报告不算用户学会或真实经营行为 |

桥接操作冻结source revision与目标上下文，显示预览，确认后以请求身份原子保存。失败重试优先确认既有结果，不重复创建观察/实验。

## 8. 旧案例的后续追踪

用户可在读案例时登记可核对的预期、期限及所需材料，例如价格/规格/公开承诺是否改变；不是自动预测商家销量或利润。到期按相同口径补新快照，显示支持、推翻或仍未知及原文。

更新附在旧案例和今日页的“旧案例后续”中，不占新的主案例。没有相同范围的新材料时保留未知；某次返回列表没出现，不直接等于商品下架、店铺倒闭或退出榜单。

## 9. 四期交付

| 期 | 交付 | 完成判据 |
| --- | --- | --- |
| A 材料与每日唯一案例 | 店铺身份、冻结材料、稳定每日槽位、乐天搜索/排名适配、小红书手动材料 | 同店不重复、并发不换案例、所有数值可追溯；材料页本身可用 |
| B 一篇可核对的拆解 | 结构化AI草稿、授权与校验、分层阅读、对照、方法/未知/动作及预览桥接 | 手动确认选题即可读完整案例；无材料的章节保留未知，不造销量 |
| C 每日自动准备 | 轮换候选池、独立来源预算/租约、自动生成范围授权、默认关闭cron | 有材料且获授权才生成；重复worker不重复调用/发布，失败可见可停用 |
| D 多平台与长期学习 | 小红书材料完善、已确认跨平台主体修正、条件化方法检索、旧案例追踪/周复盘 | 新主案例保持唯一；更正影响能回查，复用方法保留条件 |

A/B是首个可用闭环，C实现完整每日自动体验，D拓展来源与长期复查。每期有独立开关和验收，代码存在不等于来源接通或生产定时器已开启。

## 10. 验收红线

- 同店不同SKU、同天多设备、失联重试、并发worker都不能产生第二个主案例。
- “每包12枚”、一条评论“买3盒”、累计下界、评价数不能互相换算。
- 没有公开销量也可研究生意，但标题不得称已证明热销；热销解释必须体现依据范围。
- 来源原话保持原样；字段名或枚举翻译不能改写quote/text。
- 用户私有数据不因旧AI许可被发送；撤回自动许可后禁止新请求并丢弃未授权在途输出。
- 看完、跳过、保存方法和AI报告均不新增validation、不改想法状态/last_activity_at、不触发或调整锁机制。
- 获取失败、材料缺失或过期报告不能被伪装为当日成功；所有分母、利润与人群未知可见。
