# 競合する説明と、撤退した生意を読む

2026-11-20。ユーザーが選択した案1・4の具体設計。機能の方向は承認済み。この仕様のレビュー後に実装計画へ進む。自動収集の追加料金枠はまだ有効化しない。

## 目的と既存コード

同じ観察を説明できる別の仕組みを並べ、何を調べれば区別できるかを残す。売れている事業だけでなく、撤退・縮小した事業の条件も調べる。分析を実需要の検証とみなさない。

既存の報告には `text / competingExplanation / distinguishingObservation` がある。`research` には出典付きの退出・縮小研究があり、`failure` の保存契約と原文の無効化処理もある。両者を拡張し、同じ用途の記録システムをもう一つ作らない。一级导航は追加せず、すべて既存の `business-lab` 内に置く。

## 検討した構成

1. **推奨：既存の説明を比較・調査につなぎ、撤退事例を独立した教材枠で読む。** 現行の報告、調査結果、方法、研究記録を再利用できる。撤退教材には会社・事業・店舗・商品という対象範囲が必要なので、楽天／小紅書の店IDを偽装して使わない。
2. 報告の文章だけを増やす。実装は小さいが、読んだ後の確認行動と履歴が残らない。
3. 日次の店選びを全面的にWeb検索へ置き換える。既存の公式榜単選出・重複防止・費用上限の変更が大きく、今回の目的から広がる。

## A. 同じ観察に対する説明を比べる

入口は報告の説明ごとの「这两种解释，怎样区分？」。報告ID・版・章・説明位置・入力ハッシュを固定して開く。既存の本人の研究とは区別し、元のAI説明は変更しない。

最初は現在の報告に保存されている説明Aと競合説明Bを並べる。どちらにも引用があるとは限らず、引用がない説明はそのまま仮説と表示する。現在の資料がA/Bを区別できなければ「尚不能区分」。説明の正しさ・人気・確率の点数は付けない。初版で数合わせの第三仮説を生成しない。

本人は、同じ対象・条件・期間について次を編集する。

- 比べたい観察／問い。
- Aが成り立つなら、次に何が観察されるはずか。
- Bが成り立つなら、次に何が観察されるはずか。
- 何が見つかれば、自分が採っている説明を捨てるか。
- 調べ方と期限。

公開情報だけで調べる方法も選べる。価格・配送・露出など複数条件が同時に違う比較では、何が未統制かを本人が明記できる。どちらの予想とも異なる結果を排除しない。

プレビュー後、明示保存したものだけを確認計画とする。既存の確認計画・結果・次の計画・方法の流れへつなぐため、計画の出自に「説明比較」を追加する。現在のシミュレーション／調査結果由来の計画はそのまま読める。元の比較の版を固定して参照し、後から書き換えて事前予想をすり替えない。

実施後は既存の結果入力で、実際に調べたもの・分かったこと・出典・考えの変化を保存する。事前のA/B予想を横に表示する。AIやコードがA/Bの勝者を決めず、両方では説明できない／まだ分からない状態を本文で残せる。そこから次の確認計画や本人方法に進める。

元の報告が消えたら、報告からの引用とAI説明は再表示しない。本人が独立して書いた計画・予想・結果は残し、元の出典が読めない旨を示す。比較本文の消去は、関連するキャッシュ・版・凍結参照にも既存の物理消去方針を適用する。

AI呼出しは増やさず、最初は保存済み報告の二つの説明を利用する。後から生成方式を変える場合も、過去報告の版を上書きしない。

## B. 撤退・縮小した事業を教材にする

生意拆解の中に「退出与收缩：哪些条件没能持续」枠を追加する。既存の今日の楽天店を置き換えず、教材は東京日付ごとに最大一件。毎日公開したことと、その出来事が起きた日付を分ける。過去の事例も対象にする。

教材の構成：対象と範囲、当時の提供物と想定した客、何が終了／縮小したか、発表日・実施日、会社が説明した理由、別の説明、まだ不明な条件、次に区別するための材料。会社自身の理由は「発表した理由」と記し、因果が証明されたとは書かない。公表文に理由がなければ「理由は公表資料から確認できない」。

閉店・商品終売・事業撤退・会社倒産を混同しない。発表予定と実施済みも別に扱う。公式URLが読めない、検索結果に出ない、商品が下架した、ランキングから消えたことは、撤退を確認する根拠にしない。

### 収集と公開

最初は、原文を取得できる公式発表を使う。対象の会社／サービスと発表元の対応を確認できるドメインの登録を必要とする。検索結果やAIが言う「公式」だけでは発表元を承認しない。任意サイトの自動巡回や、ログインが必要なページへの接続は行わない。

候補には原URL、発表元、取得時刻、公開日、対象範囲、日付、出来事を述べた連続原文とハッシュを保存する。予告・実施・理由の各主張はそれぞれの原文に結び付ける。校正不能な対象や出来事は公開しない。校正を通った出来事だけ読めて、分析が欠ける場合は分析の欠落を明示する。除外されたAI出力・理由・validator版は、通常表示と分離して診断用に保存する。

第一段階は確認済み候補キューの中から日次選出する。実装・テスト用の架空事例を本番キューに入れない。対象・市場・事業単位を正規化した識別子で重複防止する。同じ事業の別URL、発表記事と続報を別教材として毎日出さない。対象が違うと確認できない同名ケースは保留する。

確認済み候補がなければ、新しい教材がないと表示する。既読の教材は履歴から読める。候補不足を埋めるために未確認事例を公開しない。

### 自動収集の範囲

コードと設定画面は用意するが、新しい収集は初期状態で停止する。既存の「公式楽天フィールドのみ送信」の許可は、他社公式発表のWeb検索・本文送信の許可に流用しない。

有効化の提案は主账号限定、東京時間の日次で最大2回の検索、3ページ取得、1回のGemini分析。検索プロバイダーのフォールバックも実リクエストごとに枠を消費し、上限で止める。失敗・応答不明での自動AI再試行はしない。既存の楽天12 HTTP／1 Gemini枠とは独立して明示し、有効化前に本人が追加枠と送信対象を確認する。私的メモ・連絡先・未選択の材料は送らない。

日次選出だけなら、既存の確認済みキューから選ぶため外部呼出しは不要。既存のGitHub Actionsのcron認証と主账号制限を再利用し、一般登録ユーザーには自動料金が発生しない。

### 既存機能との接続

教材から、出典を選択して既存の退出・縮小研究を始める。一般企業の教材を楽天店として登録せず、研究のケース参照で教材と店舗を明確に区別する。教材と売れている事業を並べる際は対象市場・時点・客・課金・交付条件を示す。似ているから同じ原因とはしない。

教材内の複数説明もAと同じ比較・確認計画へつながる。教材を読んだことや確認計画を保存したことは、`validations`、`ideas.status`、接触時刻を書き換えない。学習内容は本人が確認して方法へ進める。

## 技術と検証

- Next14 / TypeScript / shadcn / Tailwind、既存の `lib/ai` facade、Supabase client/RPCを維持する。
- DB所有者はサーバーでログインから解決。private helperはclient実行不可、公開RPCはservice限定、固定search_path、RLS、型・長さ・版・出典の一致をDBでも検査する。
- requestIdと内容ハッシュで再送を同じ操作として扱う。応答不明で別IDを作らず、保存と再読込失敗を区別する。古いレスポンスが消去済みの本文を戻さない。
- 計画起点の追加に伴い、既存のシミュレーション計画・followup・結果・履歴・workspace・方法の実SQL回帰を行う。全件を新形式へ偽装変換しない。
- 候補収集はHTTP/Gemini依存を注入し、同じ事業の重複、予告と実施、対象違い、原因未公表、原文不一致、部分分析、失敗・再送・並行実行・予算上限・主账号外・停止をテストする。
- 実ブラウザーで説明比較→計画→結果、教材→退出研究、消去後の再訪とフォーカス再読込、スマホとコンソールを確認する。
- マイグレーション番号は実装時のmainをfetchして決定し、`schema.sql`へ同じSQLを追記する。本番にテスト記録を作らず、実際の本番デプロイの成功を確認する。

## 実装順

1. 既存報告からの説明比較と、確認計画・結果・履歴への接続。
2. 公式発表を持つ撤退教材、重複しない日次選出、既存研究への接続。
3. 制御された自動収集・設定・診断記録。有効化は送信対象と追加予算の確認後。
4. 両機能を合わせた回帰・実SQL・ブラウザー確認と公開。

仕様レビュー：既存機能との重複、成功／失敗の決め付け、原文消去、店IDの偽装、追加費用の暗黙拡大を避ける構成とした。日次候補不足は明示する。未知を埋めるための生成は行わない。
